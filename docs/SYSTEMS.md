# Where the seconds go

Evaluation is the largest cost in five of the six configurations I profiled. Faster training environments help, but they only account for 22–27% of an ARS or CEM run.

The measurements are in [results/bench/summary.json](../results/bench/summary.json), generated by [`bench_summary.py`](../bench_summary.py). The [reset comparison](../results/bench/native-reset-gate.json) contains the larger C correctness check.

## Measurement setup

I pinned each process to CPU 4, a Zen 5 core of the AMD Ryzen AI 5 PRO 340, with a 4.9 GHz maximum. The governor, energy preference and platform profile were `performance`. NumPy, BLAS, XLA and EnvPool each used one thread. This chip also has slower cores; the main README measurements were unpinned. [Machine details](../results/bench/machine.json) include versions and CPU settings.

Each backend/task pair ran in five new processes. Batch sizes were shuffled within each process. Random actions were fixed. At batch size B, each process timed `max(128, 8192/B)` calls after 32 warm-up calls. Gymnax-scan instead timed `max(16, 1024/B)` calls of 64 fused steps. Timings include explicit resets; reset-only slots in next-step backends do not count as transitions.

Before timing, each backend steps 64 copies from its reset states, with Gymnasium following the same states and actions. Rewards and termination must match exactly; observations must agree within `1e-4`. All 11 backend/task pairs passed in all five processes. Maximum observation differences were zero for NumPy and Gymnasium, about `2e-7` for EnvPool and `5e-6` for float32 Gymnax.

The first three processes saw a one-minute load average of 2.2–2.6, versus about 1.1 for the last two. Gymnasium's large sequential batches ran 10–25% faster in the latter processes. The tables use all five processes ([run window](../results/bench/window.json)).

Gymnasium has no vectorized Acrobot. At B=4096, my NumPy Acrobot runs 140× faster than its sequential wrapper and 2.5× faster than single-thread EnvPool.

CartPole is dominated by resets. At B=4096, both NumPy implementations spend about 137 µs in a step call. Mine then creates a NumPy generator for each restarted slot to match `reset(seed=s)`, costing 6.6–10 µs per reset. Resets consume 90% of its time at that size. Gymnasium's vectorized CartPole draws all resets from one generator.

Small batches pay for Python calls: at B=1 my NumPy step takes 25 µs on CartPole and 87 µs on Acrobot. ARS and CEM train at B=64; CartPole PPO uses B=8.

Gymnax's first call at each batch size takes 233–515 ms on CartPole and 374–821 ms on Acrobot. A whole ARS CartPole qualification uses about 0.14 million training transitions, making compilation expensive relative to the work.

The fused Gymnax rows keep observations on device. Their original timing runs checked the unfused step path. A later `scan_trace` check compares 64 fused and unfused steps from the same PRNG key, requiring matching episode counts and final states within `1e-5`. Both tasks' final states matched exactly; CartPole completed 171 episodes in each path. Acrobot completed none, so that short trace does not exercise its reset path. A mutation test checks that corrupted fused states are rejected.

## A fused C batch

I rewrote the two batches in [`classic.c`](../control_clock/classic.c), loaded through ctypes. One call steps the batch; another resets any set of slots from their seeds. It uses the same NumPy arrays and API ([implementation details](ENVIRONMENTS.md#fused-c-batch)).

The reset check matched Gymnasium bit for bit on 1,010,006 seeds per task: seeds 0–999,999, six boundary seeds from 2³²−1 to 2⁶⁴−1 and 10,000 random seeds above 2³². It compares both float32 observations and internal states. The laptop used NumPy's AVX512_SKX float32 trigonometry path.

The C batch also passed the ordinary Gymnasium dynamics tests. In every timed process, a 64-step, 64-slot trace matched NumPy bit for bit, including inactive slots and internal states. Longer tests cover 1,500 steps and resets. Six source mutations test the checks themselves: three alter resets, and three alter dynamics. Even the changed RK4 weight and summation order, which stay inside Gymnasium's tolerance, fail the exact NumPy comparison.

### C and NumPy measured together

I timed both batches in a second run using the same core, workloads and thread settings, with five processes per task ([machine](../results/bench/native-window/machine.json), [window](../results/bench/native-window/window.json)). Million transitions per second:

| CartPole-v1 | B=1 | B=8 | B=64 | B=512 | B=4096 |
|---|---:|---:|---:|---:|---:|
| NumPy | 0.040 | 0.310 | 1.42 | 2.75 | 3.16 |
| C | 0.430 | 2.54 | 10.9 | 30.5 | 41.3 |

| Acrobot-v1 | B=1 | B=8 | B=64 | B=512 | B=4096 |
|---|---:|---:|---:|---:|---:|
| NumPy | 0.012 | 0.092 | 0.650 | 2.46 | 4.09 |
| C | 0.420 | 2.23 | 4.97 | 5.95 | 6.10 |

Interquartile ranges are within 4% of each median. C is 7.7–13× faster on CartPole and 1.5–35× on Acrobot. At B=4096, a CartPole reset costs 0.12 µs per slot instead of 6.35 µs; resets fall from 90% to 22% of batch time. At B=1, C step calls take 2.2 µs on CartPole and 2.4 µs on Acrobot.

NumPy ran 3–10% faster in this second run than in the first. The C-to-NumPy ratios above compare measurements taken together.

### Effect on a complete run

Training-environment steps and resets take 22–27% of the median ARS/CEM run for each configuration, and at most 29% of any of those 20 profiled runs. For PPO the share is 2–3%. Amdahl's law therefore caps the benefit of faster training environments at roughly a quarter for search, even if simulation took no time.

The C batch has only been timed as an environment backend. All qualification results still use NumPy.

## Training phases

I ran seeds 0–4 of each of my three methods twice: once normally and once with [`phases.py`](../control_clock/phases.py) timing calls around each phase. Order alternated by seed. All 30 normal and 30 profiled runs matched every evaluation in the original records, including step counts and all 100 returns.

The phases account for each solve clock to within 0.05%. Profiling added a median 0.005–0.018 seconds in four configurations, 0.15 seconds for Acrobot CEM and 0.87 seconds for Acrobot ARS.

## Saved policies and a fresh evaluation cohort

ARS, CEM and batched PPO save their passing policy after the clock stops. SB3 and CleanRL do not. Saving is skipped within ten seconds of the deadline to leave room before the parent watchdog fires. [`policies.py`](../control_clock/policies.py) stores parameters, task, threshold, evaluator and package versions, then checks the rebuilt policy's actions and returns against the live policy. An action SHA-256 is saved for replay.

New records include the source revision and tracked-file edit status. The 30 policies measured here have `"source": null`: [machine.json](../results/bench/machine.json) identifies revision `18cd145` at the start of the run; the training and policy code was unchanged through the `bench.py` fix at `8dd2203`. Their tracked-file edit status was not saved.

[`replay.py`](../replay.py) starts a new process, requires matching returns and action digests on the 100 protocol episodes, then evaluates 1,000 episodes with seeds 2,000,000–2,000,999. Those seeds were unused in training, stopping or configuration selection. All 30 policies reproduced their original evaluations ([replay results](../results/bench/replay.json)).

| Configuration | Median selection mean | Median new-seed mean | Passing on 1,000 new episodes | Passing 100-episode blocks |
|---|---:|---:|---:|---:|
| CartPole ARS | 486.5 | 486.2 | 5/5 | 50/50 |
| CartPole CEM | 492.7 | 495.6 | 4/5 | 40/50 |
| CartPole PPO | 500.0 | 500.0 | 5/5 | 50/50 |
| Acrobot ARS | −96.2 | −99.3 | 4/5 | 31/50 |
| Acrobot CEM | −97.7 | −97.4 | 4/5 | 36/50 |
| Acrobot PPO | −93.9 | −96.1 | 4/5 | 37/50 |

The first passing evaluation often selects a policy near the threshold. Four of the 30 fell below it on 1,000 new episodes. Acrobot's 100-episode block counts pool ten blocks from each of five policies; they describe those policies, rather than a new independent set of 50 training runs.

## Reproduce

```sh
uv sync --frozen --python 3.12 --extra jax --extra bench
.venv/bin/python -m control_clock.native build
.venv/bin/python -m control_clock.native verify --seeds 1000000 --output results/bench-replication/native-reset-gate.json
.venv/bin/python bench.py all --output results/bench-replication --cpu 4 --reps 5
.venv/bin/python bench.py env --backends numpy,native --output results/bench-replication/native-window --cpu 4 --reps 5
.venv/bin/python bench_summary.py --input results/bench-replication --output results/bench-replication/summary.json
.venv/bin/python replay.py --input results/bench-replication/decompose --output results/bench-replication/replay.json
```

Choose a full-speed core on your machine and keep it otherwise idle. EnvPool 1.2.7 loads `libEGL.so.1`, `libOpenGL.so.0` and `libGLdispatch.so.0`; Ubuntu packages them as `libegl1`, `libopengl0` and `libglvnd0`. `bench.py --jax-platform` selects the JAX platform; other backends are CPU-only.

## Remaining limits

- One laptop, one core and one thread; this does not measure multicore scaling.
- Five processes per throughput measurement, with some background-load variation. C was measured in a separate run from the other backends.
- Profiling and new-seed replay cover five seeds of my three methods. The library PPO runs and remaining seeds have no phase breakdown or saved-policy replay.
- Dynamics tests cover finite trajectories and boundary cases. Gymnax uses float32, and C's bitwise checks have only run on x86-64 Linux with glibc and NumPy's AVX2/FMA3 trigonometry.
- The NumPy evaluator and C training batch have been timed separately; neither changes the main qualification results.
